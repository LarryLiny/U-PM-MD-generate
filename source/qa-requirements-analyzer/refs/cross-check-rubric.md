# 第五步：requirements.md 覆盖度交叉检查

<!-- agent 原文标题为 `### 第五步：requirements.md 覆盖度交叉检查` -->

生成 requirements.md 后，必须执行一次覆盖度交叉检查，确保 requirements-analysis.md 中所有已定义的检查点都在 requirements.md 的 AC 中有对应。

**检查方法（强制逐行对比，禁止整体扫描）：**

> ⚠️ 禁止用"整体看一遍觉得差不多"的方式做交叉检查。必须按以下步骤机械化执行。

**步骤 0：优先跑脚本**
如果 `scripts/cross-check.py` 可用，优先执行脚本自动对比。脚本会输出未覆盖项列表。如果脚本不可用或报错，按步骤 1-5 手动执行。

**步骤 1：生成对比表（强制输出，不可省略）**
遍历 analysis 中每个元素的每个"需补充=否 且 PRD/原型有定义"的检查点，输出如下格式的对比表：

```
| 元素 | # | 检查点 | 对应 AC | 覆盖？ |
|------|---|--------|---------|--------|
| C01  | 1 | Logo 点击回首页 | AC-01-01 | ✓ |
| C03  | 4 | 遮罩层点击关闭 | ??? | ❌ 遗漏 |
```

- 每一行必须填写对应的 AC 编号，填不出来的标记 ❌
- 对比表必须完整输出到 analysis 的交叉检查章节中（或作为执行过程的中间产物展示给用户）
- **禁止跳过任何一行**，即使"觉得肯定覆盖了"也必须写出 AC 编号

**步骤 2-5：同原有流程**
2. 对每个元素中"是否需要产品补充=否"的检查点，在 requirements.md 的 AC 表格中查找是否有对应的规则覆盖
3. 重点检查以下容易遗漏的场景：
   - 原型有实现但 PRD 未明确描述的交互细节（如动画、hover 效果、遮罩层行为等）
   - 通用交互规范类检查点（loading、防重复提交、网络异常）是否需要在 AC 中显式体现
   - "交互一致"引用的模块，其差异参数是否在 AC 中体现
   - 待产品确认的检查点是否在 AC 中标记了「⚠️ 待产品确认」
   - **业务规则（BR-xx）中的每条规则**是否都有对应 AC（容易因为"觉得是通用规则"而遗漏）
4. 发现遗漏的，直接补充到 requirements.md 对应的 AC 中
5. 在 requirements-analysis.md 末尾输出交叉检查结果摘要：覆盖的 AC 数、遗漏数、已补充数

**同步检查清单（容易遗漏项）：**

除了逐元素对比外，以下全局一致性检查也必须执行：

- **状态机与 AC 一致性**：状态机中的 trigger 文案、断言文案必须与 AC 中的描述完全一致（如按钮文本、弹窗文案）
- **权限矩阵操作命名**：权限矩阵的操作命名必须与 AC 中的功能名称一致（如"发布首页" vs "发布各 Tab"）
- **用户故事与 AC 对应**：每条 US-xx 必须能映射到至少一个 AC，且描述风格一致
- **测试范围描述与 AC 一致**：测试范围表格中的"功能点"必须与 AC 的覆盖范围一致
- **附录（字段长度、图片格式等）与 AC 边界值一致**：确保附录汇总表与 AC 表格的"边界值"列数据一致

**什么样的检查点需要体现在 AC 中（判断规则）：**

| 分析文档中的标记 | 是否需要在 AC 中体现 |
|-----------------|-------------------|
| 需补充=否，且 "PRD：xxx" | ✅ 必须体现 |
| 需补充=否，且 "原型：xxx" | ✅ 必须体现 |
| 需补充=否，且 "PRD/原型未定义（通用交互规范）" | ✅ 必须体现（作为通用规范 AC） |
| 需补充=否，且 "PRD/原型未定义（不适用）" | ❌ 不需要体现 |
| 需补充=是（待产品确认） | ⚠️ 标记为"待产品确认" |
| 需补充=—（必填=否且未定义） | ❌ 不需要体现 |

**输出格式：**

在 requirements-analysis.md 的「断言覆盖统计」章节后追加：

```
## 九、交叉检查结果

### 本轮新增/修正的 AC 项

| # | 遗漏项 | 补充位置 | 状态 |
|---|--------|---------|------|
| 1 | xxx | AC-xx-x | ✅ 已补充 |

### 交叉检查最终结果

| 指标 | 数值 |
|------|------|
| 分析报告已定义检查点总数 | N |
| requirements.md AC 已覆盖数 | M |
| 本轮遗漏并已补充数 | K |
| 覆盖率 | M/N |

### 未体现在 AC 中的检查点（合理排除）

列出 PRD/原型未定义且不适用的检查点，说明为何不需要体现。
```

**迭代检查策略（若用户要求"再检查一遍"）：**

每次执行交叉检查时，不仅对比单个元素的检查点，还需：
1. 检查全局一致性项（状态机、权限矩阵、用户故事、测试范围、附录）
2. 检查文案精确性（弹窗文案、提示文本、按钮命名是否与 PRD/原型字面一致）
3. 检查跨 AC 引用的合理性（"同 AC-xx"的引用是否能还原完整规则）
4. 检查必填项描述的具体性（避免"应有校验提示"这类模糊描述）
