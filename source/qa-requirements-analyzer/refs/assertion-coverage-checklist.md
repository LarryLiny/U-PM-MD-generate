# 断言覆盖执行规范

断言覆盖是 #1 自检项的核心环节，按以下 6 步执行，结果输出到 `requirements-analysis.md` 的"断言覆盖详情"章节。

> 注：实际执行步骤为 7 步（步骤 6 拆分出"未归类业务规则"，步骤 7 拆分出"PRD 全文段落扫描"）。原 agent 标注"6 步"是历史命名，实际内容按 7 步展开。

**归类方法：**
- 一个功能流程中的元素分别归到对应的类型（如新增弹窗里的输入框归纯文本、上传归上传、保存按钮归提交）
- 同一个元素只归一个类型，选最贴合的
- **触发类 vs 提交类**：触发类点一下就完成操作，不依赖前置操作（如上架/下架、加入首页展示）；提交类必须先完成前置操作（如填表单），否则无法提交。搜索、筛选等辅助操作不算前置操作
- **只读信息**：独立详情页/查看弹窗中的只读信息归详情/查看；编辑表单中的只读字段跟着新增/编辑验证；打开查看类按钮归弹窗/抽屉（容器）+ 详情/查看（内容）
- **静态文案**：能关联到某个元素的跟着关联元素验证，不单独归类；纯独立的静态文案不在覆盖范围内
- **是否必填**：是=产品必须定义该检查点的内容；否=取决于产品是否定义了该功能

**补充判定规则：**
- **必填=否且产品未定义时不建议补充**：如果某检查点的"是否必填"为"否"，且 PRD/原型均未定义，则"是否需要产品补充"填"—"，不建议产品补充。只有"是否必填=是"且 PRD 和原型都未定义时才标记需要补充
- **原型定义等同于 PRD 定义**：如果 PRD 未定义某检查点，但原型代码中有明确实现，视为已定义（标注"原型：xxx"），不需要产品补充
- **未归类业务规则也按标准格式输出**：第 6 步发现的未归类业务规则，也必须按与归类元素相同的表格格式输出（含检查点、PRD/原型内容、是否需要补充），并标明"需补充：是/否"
- **交互一致的元素可合并但需补充时必须展开**：PRD 标注"交互一致"的模块，如果所有检查点均不需要补充，可以引用已展开的元素（标注"检查点同 Cxx，不再重复展开"）；但如果有任何检查点需要补充，则必须完整展开所有检查点，不可省略
- **元素拆分粒度：入口拆分，流程内不拆分**：不同的功能入口应拆分为独立元素（如新增按钮 vs 编辑按钮，两者表单初始状态、成功提示文案不同）；同一操作流程内的子步骤按钮不单独拆分为元素（如确认按钮、取消按钮属于编辑流程的一部分）。判断依据：**是否有独立的触发场景**
- **跨模块的相同功能不抽象为公共章节**：即使多个模块有相同的功能（如多个 Tab 都有发布功能），也应分别展开在各自模块中，不要抽象为公共章节。原因：每个模块的前置条件、校验规则可能不同（如 A 模块发布无必填校验，B 模块发布需最少1条），公共章节会丢失模块特定的细节信息
- **🔴 信息密集只读元素下钻字段级（列表/详情/图表）**：归类为「7.列表」「16.详情/查看」（含雷达图/柱状图等图表）的元素，不能只查"数据正确加载"，必须**逐列/逐字段/逐数据点**核对 PRD 是否定义其**含义/数据来源/计算口径/格式单位/枚举取值/显示规则（色阶·阈值·小数位）**——聚焦有计算·聚合·枚举·口径·色阶的**业务字段**（纯展示字段如姓名/序号免）。标题有、字段级规则无 → 该检查点需补充=是；**缺口按元素合并为一个 D-xx**（注明哪几列/几维未定义），不逐字段拆 D。对应通用断言库 7#13 / 16#9。
- **🔴 精确文案必须 100% 可溯源（不得虚构）**：AC 表格中任何"精确文案断言"（如抽屉标题、Tooltip 文案、弹窗文案、按钮文字、时间格式、错误提示等原子字符串）**必须在 PRD 文档或原型 DEMO 源码中能找到对应字符串**，并在分析表的"PRD/原型内容"列标注来源（格式 `原型：HomepageConfig.tsx:203 okText: '确认切换'`）。若 PRD/原型未定义具体文案，则该检查点**只能写"应有该提示/标签"的结构性断言**（如"应展示副标题区域"），不得凭经验生造具体文字。反例：PRD 说"抽屉带副标题"→AC 写"标题为「发布历史 - 基础配置」"这是**虚构**，会把"产品实现与自己想象不一致"误报为 Bug，直接浪费研发排查成本，并让产品失去对需求文档的信任。所有"精确文案类"AC 在评审时单独列表做溯源核对

**执行步骤：**

> 🧪 **断言化试金石（贯穿第 3-5 步，强制）**：填每个**必填**检查点的"PRD/原型内容"时，先自问一句——**「这能写成 `expect(具体可观测).toBe(具体值)` 吗？」**
> - **具体值** = 带引号的字面文案 /「数字」/ 路由(`/login`) / 枚举 / 布尔 / 可见·隐藏 / 启用·禁用 / 跳转目标 等**可观测态**。
> - **模糊词（不算具体值）** = 正确 / 正常 / 符合预期 / 符合要求 / 无误 / 友好 / 合理 / 适当 / 恰当 / 清晰 / 流畅 / 良好 / 准确。
> - **判定**：① 必填检查点 PRD/原型只给模糊词（如"排序正常"却无排序规则、"提示正确"却无文案）→ **视同未定义** → 需补充=是（D-xx）；② 给了具体值 → 需补充=否；③ 非必填且只有模糊描述 → 标"—"。
> - **目的**：把"写脚本时才发现 `toBe(?)` 填不出"的痛，提前到分析阶段就地暴露。**填不出具体值 = 缺口，不许用模糊词蒙混过去**。
> - 脚本兜底：`count-coverage.py` 扫"必填检查点 PRD/原型内容为空"（empty_required_content 应为 0）；阶段二 `validate-requirements.py` check 15「断言具体性」对纯模糊词断言 WARN。

> 🚦 **可测性三问（紧接试金石，对每个必填检查点再过一道）**：试金石管"PRD 有没有给具体值（定义层）"，可测性管"即使有值、测试人员实际能不能测（执行层）"。三问命中任一 → 标"疑似不可测"：
> 1. **前置态可构造吗**：测试人员能否靠自己可控手段切到该状态？❌ 信号：本期下线 / 灰度中 / 后端开关控制 / 依赖无法申请的权限或外部系统态。
> 2. **断言点可观测吗**：结果在可见 UI（文案/元素/跳转/状态）还是内部/缺失态？❌ 信号：缺失态（"不渲染/不存在/不发送"）、纯内部态（日志/埋点/后端字段）黑盒看不见。
> 3. **核对清单是有限确定集吗**：❌ 信号：开放集（"其它 XX""…等""各种…"）无法穷举核对。
> **分流（不是删，是改造或标记）**：
> - **能补全 → 就地改造成可测**：前置态给可控构造途径（mock/测试开关/造数据步骤/降级到可达等价态）；缺失态改成正向可观测断言（"不展示 X"→"应不出现 X / 应展示占位"）；纯内部态找 UI 可见代理，或降级为接口/日志断言并注明观测手段；开放集推动产品给**有限确定清单**并逐项列出。
> - **无法补全（预判确实测不了）→ 标 🚫 不可测**，作为一类缺陷写进「四、缺陷汇总」（D-xx，注明命中三问哪条 + 等待方 产品/研发），不静默丢弃。
> - 脚本兜底：`count-coverage.py` 扫检查点含"下线/灰度/后端开关/不渲染/不发送/其它/…等/各种"等信号词 → WARN 提示需分流。
>
> 🧪 **白盒越界识别（第 2 问"可观测"的高频踩坑：把系统/开发视角写进黑盒功能预期）**：黑盒功能测试员手里只有界面，下列"系统内部量"在 UI 上看不见，**禁止写进功能用例的前置/预期**——
> - 字段内部取值口径（从哪个登录态/接口取、各端怎么取）；
> - 内部数据表示（如"暂无院校"在系统里是空值 null 还是标识 flag）；
> - 路由/跳转参数、URL query、内部 ID（如"跳转参数含任务 ID"）；
> - 后端字段值、接口入参/出参、是否调用了某接口。
>
> **正确分流（按测试类型，不是删）**：
> - ①**功能层**只断言**可观测现象**（跳对页面、页面内容确属该对象、列表只出现该见的项、文案/状态正确）；前置态写成**可构造**的（如"用一个'暂无院校'测试账号"），不写内部取值口径；
> - ②取值/参数/ID/是否调接口等校验**下沉到接口测试层**，登记到「接口测试消费顺序」；
> - ③若本需求**接口测试 N/A**（接口由后端出、不在本期测），这些白盒项**不在功能流水线作为阻塞待确认**——功能层只要"前置可构造 + 断言可观测"即视为可测、不卡流程。
> - 判据一句话：**界面看得见 → 功能层断言；界面看不见 → 接口层（接口 N/A 则不作功能阻塞）**。
> - 脚本兜底：`count-coverage.py` 的 `whitebox_audit` 扫元素检查点行含「前端不重排/不在前端/落点在后端/按…ID 匹配/是否调…接口/接口入出参/后端字段」等白盒信号词 → WARN 提示需分流（正则巡检、warn 级、只扫元素检查点表格行、不碰实体结构/来源列）；用例侧 `validate-format.py` 的 `check_whitebox` 同规则扫用例步骤/预期。二者是"已定义该怎么做"的机械兜底，命中不等于必错，但必须逐条人工复核分流。
>
> 🗣️ **实现术语泄漏（与白盒越界互补：现象可观测，但用错了语言）**：界面**看得见**的现象，必须用**用户感知语言**写预期，**禁止**把数据契约/字段定义原样搬进预期结果——如 `data-source=teacher`、`type=library/custom`、`skill=listening`、`progress`、各类枚举码值。功能测试员/验收方手里只有界面，只认「老师布置」标识、「听力」标签，读到 `data-source=teacher` 会困惑、无法对照界面判定通过与否。
> **术语翻译规则**：
> - ①预期结果的**主语只能是用户能看见/能操作的现象**（"显示「老师布置」标识"、"归到「听力」分类"、"进度条走到 100%"）；
> - ②字段名/码值最多作**括号补充**（"显示「老师布置」标识（data-source=teacher）"）或挪到**来源/备注列**，**不作预期主语**；
> - ③若某码值在界面**没有任何可视表征** → 这已不是术语问题，回到上面「白盒越界识别」分流（下沉接口层）。
> - 🔒 **不翻译的例外（PRD 已定义的精确文案）**：PRD/原型已给的用户可见精确文案（弹窗文字、按钮文案、提示语，如「该商品不在您的院校销售范围」）本就是用户语言，**字面照搬、不得改写翻译**——术语翻译只针对字段名/码值（data-source=teacher），不碰精确文案。与「精确文案必须 100% 可溯源（不得虚构）」及 cross-check 同步检查清单的"文案精确性"互为呼应。
> - ⚠️ **作用域（分析层专属，防语义偏差）**：本条只管 **AC 的预期断言措辞**用用户感知语；**不等于"分析文档里禁止出现字段名"**。业务实体结构（章节六）、数据约束、来源标注列**必须保留字段名/类型/枚举码值**——那是数据契约的权威记录。分析层的独特职责是**建立"用户现象 ↔ 字段码值"映射**（在 AC 用括号桥"「老师布置」标识（data-source=teacher）"、在实体结构记字段），供下游用例生成器据此把预期翻成纯用户语。**删字段名 = 抹掉契约 = 下游丢映射只能猜**，比术语泄漏更糟。
> - 📄 **两文件分工（回溯优先级）**：
>   - `requirements-analysis.md`（**产品可见**）：本职是与 PRD **可逐条回溯**。断言覆盖表的「PRD/原型内容」列与「PRD：xxx」来源标注是**回溯锚，照引 PRD 原文/字段名/章节号，术语翻译一律不改**；只有"检查点/断言描述"用业务语表达。**保证产品看 analysis 时与 PRD 对得上**，不因翻译偏离原文。
>   - `requirements.md` 的 AC + 下游用例预期结果：才是术语翻译的**主要落点**（给测试员照测，用用户感知语；码值靠来源列 C{xx}#{n} 回溯）。
> - 一句话：**可观测但用错语言 → 翻译成用户感知语；不可观测 → 下沉接口层。翻译动的是"断言怎么说"，不动 analysis 里"PRD 怎么引"。**

1. **侦察元素**：阅读原型代码，列出所有可交互元素和动态只读数据。**必须机械化扫描**：逐行检查原型中的每一个表单控件组件（`<Input>`、`<InputNumber>`、`<Select>`、`<Cascader>`、`<Switch>`、`<Checkbox>`、`<Radio>`、`<Upload>`、`<Button>`、`<Table>`、`<Tabs>`、`<Tree>`、`<Modal>`、`<Drawer>` 等），先全部列出，再做合并判断。不可"凭理解"归纳式侦察——容易漏掉"看起来不重要"的元素（如搜索区中的某个筛选项、驱动下游逻辑的Checkbox组等）。特别注意：搜索/筛选区的每个独立筛选项都是独立元素，不可因为交互模式相似就省略。**同时注意**：原型代码侦察只能发现 UI 层面的元素，PRD 中可能存在未在原型中实现的业务规则（如"操作X时的影响提示"、"跨模块联动规则"），这些将在第 7 步 PRD 全文扫描中补充。
2. **归类元素**：按归类方法归到断言库的 16 个类型。PRD 标注"交互一致"的模块也必须完整展开，不可省略
3. **逐项填充检查点**：对每个元素展开其归类类型的**全部**检查点（不可合并行、不可省略），逐条对照 PRD 和原型填写。来源标注：PRD 定义的标"PRD：xxx"，仅原型有的标"原型：xxx"，都没有的标"PRD/原型未定义"。**文案提取规则**：当 PRD 未定义具体文案（如空状态文案、弹窗确认文案、提示语等），但原型代码中有明确实现时，必须从原型中提取具体文案写入 AC 断言（标注"原型：xxx"），不可只写概括性描述（如"展示空状态"、"弹窗确认"）。
4. **标记待补充项**：必填=是且 PRD 和原型都未定义的标"是"并写原因；必填=否的填"—"；PRD 未定义但原型有定义的填"否"。通用交互规范（loading、防重复、网络异常）不需要产品定义；业务文案（不同场景内容不同的）必须产品定义
5. **输出结论**：每个元素标题后附"需补充：是/否，待补充：#x、#y"，结论必须与表格一致
6. **检查未归类业务规则**：逐条对照 PRD/原型找出无法归入 16 个类型但有明确定义的业务规则，已覆盖的不重复。未归类业务规则也必须按标准表格格式输出。**必须机械化扫描**：
   - 逐行检查 PRD 中所有字段定义表格，将"系统生成"、"只读展示"、"自动计算"、"自动填充"类型的字段全部列出，验证是否已在某个元素的检查点中覆盖，未覆盖的作为未归类规则输出
   - 逐条检查 PRD 中的操作规则表格（如"操作-规则"对照表），验证每条规则是否已映射到某个 AC
   - 不要只关注"逻辑/计算类规则"，字段展示规则（只读字段展示什么值、怎么生成、是否可编辑）同样是可测试的业务规则
   - 当页面有多个筛选项时，必须补充"多条件联合筛选结果正确"作为未归类业务规则，确保后续生成联合筛选用例
7. **PRD 全文段落扫描（防遗漏）**：完成元素侦察后，必须回到 PRD 文档**逐段落扫描**，检查是否有未映射到任何元素或业务规则的内容。重点扫描以下类型的段落：
   - 标题含"影响"、"注意"、"说明"、"约束"、"规则"的段落（如"属性删除影响"、"类目属性变更影响"）
   - 章节末尾的补充说明段落（容易被忽略）
   - 跨模块联动描述（如"修改A模块时对B模块的影响"）
   - 数据一致性契约、下游消费约定等非 UI 交互的业务规则
   
   **扫描方法**：将 PRD 中每个段落标记为"已覆盖"或"未覆盖"。未覆盖的段落如果包含可测试的业务规则，必须补充到未归类业务规则中。纯说明性/背景性段落可标记为"不需要覆盖"并说明原因。

## 原型范围对齐（extract-elements 聚焦）

当原型/DEMO 的覆盖面**大于本期需求范围**时（典型：一个整站 demo 含登录、个人中心、订单、列表等多个需求的页面），**第一步 extract-elements.py 必须用 `--include` 限定到本期模块**，否则越界页面的元素会混入断言覆盖、放大/污染统计。

做法：
1. 先 `extract-elements.py --src <demo>` 全扫一遍，看 `by_file` 找出本期相关组件文件。
2. 再 `--include "**/Home.tsx,**/home/**,**/Navbar.tsx,..."` 聚焦重扫，以聚焦结果作为断言覆盖输入。
3. 越界文件（其他 PRD 的页面）不纳入本需求的元素清单。

> 案例：U5前台首页（首页框架+我的教程）首扫 DEMO_FROM_MD/portal 得 473 元素（含 Login/Profile/Order 等越界页），`--include` 聚焦本期模块后为 152 元素，归并同控件多态后得 36 个可交互元素/业务规则。

## 检查点展开标准（标准 B：必填全展开，非必填可省）

逐元素展开归类类型的检查点时，遵循：

- **必填（是否必填=是）检查点：必须全部展开**，一条不少。即使 PRD/原型未定义，也要列出来并标"需补充=是"或写结构性断言（如"应展示无结果空态"）。
- **非必填（是否必填=否）检查点：可在"不适用"时省略**（如导航链接没有"二次确认弹窗""loading""防重复"，可不列）；列出来标"—"也可以，但不强制。
- 元素特有的、不在 16 类标准里的检查点，可作为额外行追加。

> 自检：每个元素「是否必填=是」的行数应 ≥ 其归类类型在通用断言库里的必填检查点数。`count-coverage.py` 的「类型必填覆盖」校验会按此自动核对（各类型必填数已内置）。
>
> 各类型必填检查点数（统计自本库）：1=4, 2=3, 3=5, 4=1, 5=6, 6=4, 7=5, 8=6, 9=3, 10=2, 11=4, 12=3, 13=3, 14=6, 15=2, 16=3。
