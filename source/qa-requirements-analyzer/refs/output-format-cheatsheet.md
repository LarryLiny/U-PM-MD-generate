# 输出格式速查表

## 第三步：生成/更新需求规范

按以下 10 章结构生成 `requirements.md`：

```
# 基础信息
一、项目概述
二、测试范围（必测/可选/不测）

# 用例生成核心
三、角色、用户故事与权限（含权限矩阵+无权限 UI 表现）
四、状态机定义（YAML 格式，每条含 from/to/trigger/assertion）
五、验收标准 AC-01~N（每条含正向+反向+边界值断言）
六、业务实体结构（如题型/商品/订单的结构化输出定义）

# 接口测试核心
七、接口契约（含错误码枚举+参数边界值）

# 脚本编写核心
八、前置条件链（PRE-xx 代号）
九、并发与性能（竞态断言+性能基线）
十、多端与环境适配
```

顶部必须包含「章节用途索引」表格，标注每章对应的测试活动。

#### 页面动线索引（附表 · 放「章节用途索引」之后 · 供下游用例排序）

> **目的**：把原型里的**页面顺序 + 页内元素视觉位置**结构化保留，让 Agent2（用例生成）按"页面动线序"排列用例（而非按 AC 号），从源头消除"第 2 条就切下一页、第 3 条又跳回上一页"的乱序。
>
> **数据源优先级**：① 原型代码 —— `extract-elements.py` 的 `file`=页面、`line`=页内自上而下序（DOM 顺序），直接喂料；② 原型图 / figma 视觉动线 —— y 定上下、x 定左右；③ 都没有 → 本附表可省略（注明"无原型，动线序缺失"），下游退化到"整页加载提前 + 切页殿后"启发式。
> ⚠️ 源码 DOM 顺序遇到 `order` / `position:absolute` / `grid-area` 等视觉重排时，**以原型渲染后的视觉位置为准**修正，不盲信 line 号。

| 动线序 | 页面 | 到达方式 | 页内元素（按视觉自上而下、从左到右，标 C 代号） |
|:---:|---|---|---|
| P1 | 〈页面名〉 | 进入编辑器默认 / 由 X 到达 | C01 顶栏返回 → C02 标题 → C05 题干区 → C10 底部「下一步」 |
| P2 | 〈页面名〉 | P1 点 C10 到达 | C11 … → C20 底部「提交」 |

> **与 AC 的衔接（关键：AC 一条都不用改结构）**：每条 AC 来源列已强制带 `C{xx}` 元素代号 → 下游据此查本表即得该 AC 的 **pageOrder**（页面动线序）+ **posOrder**（页内位置序）。"整页加载/初始态"类 AC（来源列为 `—` 或页面级）posOrder 记最前（0），"切页/跳转"类记该页末尾。
>
> ⚠️ **本表只管"模块内的顺序"，不改变"按功能模块分区"这一主结构**：下游排序第一键仍是 PRD 功能模块（硬边界，同模块连续不打散），pageOrder/posOrder 只在模块内生效。

## 第四步：自迭代修复

基于第二步发现的缺陷，自动修复需求规范：

```
对每个缺陷 D-xx：
  - 可自动修复的（格式/补全/统一阈值）→ 直接修改 requirements.md
  - 需产品确认的（业务策略/功能定义）→ 在 requirements.md 中标记为"⚠️ 待产品确认，暂不测试，确认后完善"
  - 修复后在 requirements-analysis.md 中标注：D-xx ✅ 已修复
```

修复规则：
- 缺少反向断言 → 补充反向断言
- 阈值不一致 → 统一为 PRD 标准，并在规范中注明分级
- 缺少边界值 → 补充"恰好通过"和"恰好不通过"
- 缺少错误码 → 补充错误码枚举
- **权限矩阵、接口契约、并发竞态、性能基线、多端兼容性、安全（鉴权/越权/注入/XSS 等）**：如果 PRD 未定义，直接标记为"暂不测试"，不列入待产品确认清单、不标"需产品补充"。这几项属于系统级能力，产品未定义时不需要反向推动产品补充，测试范围中标注为"不测"即可；自检中记 `N/A（PRD 未定义，不测试）`并**按通过计入通过率**（不拉低通过率）。
- 状态机缺少转换 → 补充转换边
- 接口缺少参数边界 → 补充参数边界值定义
- 待产品确认的 → 标记为"⚠️ 待产品确认，暂不测试，确认后完善"

自迭代完成后，重新执行第一步自检，确认通过率提升。

同时更新 `requirements-analysis-{feature}.md` 中的缺陷状态：
- 已自动修复的：标注 `✅ 已修复`
- 待产品确认的：标注 `⚠️ 待产品确认，暂不测试`
- 在分析文件末尾生成「待确认事项汇总」章节，列出所有待产品确认的项，方便一次性与产品沟通

## requirements.md 格式要求

1. 章节按用途分组排列（基础信息 → 用例生成 → 接口测试 → 脚本编写）
2. 状态机使用 YAML 格式，每条含 from/to/trigger/assertion
3. 验收标准表格用**新格式 5 列**：`AC-ID | 验收标准 | 类型（正向/反向/边界/异常）| 断言 | 来源`。（旧格式 `规则ID | 规则 | 正向断言 | 反向断言 | 边界值` 为遗留，validate/cross-check 仍兼容，但新产物一律用新格式；`validate-requirements.py` check 4 对两种格式都认。）
4. **AC 表格"来源"列必须填写**：指向 analysis 中检查点编号（格式 `C{xx}#{n}`，多个用逗号分隔）。这是 cross-check.py 做精确 ID 匹配的依据，可大幅减少误报。agent 自行补充的总结性 AC 来源列填 `—`
4b. **🧪 AC 断言列必须能落具体值（断言化试金石）**：每条 AC 的断言要能写成 `expect(具体可观测).toBe(具体值)`——含引号文案 /「数字」/ 路由 / 枚举 / 布尔 / 可见性·启用态 等具体锚点。**禁止只写模糊词**（正常/正确/符合预期/友好/合理/清晰…）；填不出具体值说明该点 PRD 未定义 → 回 analysis 标缺口（需补充=是），不要在 AC 里用模糊词凑数。`validate-requirements.py` check 15 会对纯模糊词断言 WARN。
4c. **🧪 AC 断言必须可观测 + 用用户感知语**（requirements.md 是术语翻译主要落点，详见 [assertion-coverage-checklist.md](assertion-coverage-checklist.md)「白盒越界识别」「实现术语泄漏」）：①断言主语只能是**界面可见现象**（跳对页面/内容/列表项/文案/状态），界面看不见的白盒量（取值口径/内部 ID/路由参数/后端字段/是否调接口）下沉接口契约章节，接口 N/A 则不写进功能 AC；②不得拿字段名/枚举码值（data-source=teacher 等）当断言主语，码值只作括号补充，靠来源列 C{xx}#{n} 回溯；③例外：PRD 已定义的精确文案字面照搬、不翻译。
5. 接口契约含：请求结构、成功响应、失败响应、参数边界值
6. 已知 Bug 内联到对应 AC 下的"已知例外"子节
7. 特殊字符处理内联到对应的输入校验 AC
8. **前置条件链（第八节 PRE-xx）用账号类型，不写具体账号**：PRE 步骤里写"已注册的教师账号 / 学生账号、任意未注册账号、无院校用户账号"等类型，不写 TEA123/STU123/密码123456 等具体值（具体值属测试数据/环境配置）。这样下游用例生成可直接内联展开 PRE 步骤，无需把具体账号翻译成类型。
   - **实现术语转业务语言**：PRE 步骤里 `AuthContext / isVerified / hasSchool / phone硬编码` 等代码词改业务语言（未登录态 / 未认证态 / 无院校态 等）。
   - **路由地址保留**：第八节是「脚本编写核心」，给脚本 Agent 用（脚本要 `page.goto('/login')`），故 PRE 链**保留路由路径**（如 /login、/identify、/profile）。注意与「用例前置条件去路由用页面中文名」区分——两者受众不同（PRE 链给脚本、用例前置给人）。

### AC 来源列 ID 命名规则（强制）

来源列填 analysis 中对应检查点的精确编号，格式：

| 元素类型 | ID 前缀 | 示例 | 含义 |
|---------|--------|------|------|
| UI 可交互元素 | `C` + 两位数字 | `C13#1` | 元素 C13 的第 1 条检查点 |
| 业务规则 | `BR` + 两位数字 | `BR06#3` | 业务规则 BR06 的第 3 条 |
| 用户故事 | `US-` + 两位数字 | `US-01` | 用户故事 01（无 # 后缀，整体引用）|

**多个来源**：用半角逗号 + 空格分隔，如 `C13#1, BR04#2, BR06#1`

**特殊值**：
- `—`（破折号）：纯技术规范类 AC，无对应 analysis 检查点。**必须**在 AC 行后注释说明原因
- 留空：禁止——填 `—` 比留空更明确

**ID 一致性**：同一个 analysis 文档内 ID 必须唯一且连续。重新编号时必须同步更新所有 requirements.md 的来源列引用。

### AC 编号补丁约定（处理交叉检查后新增的 AC）

交叉检查发现遗漏并补充新 AC 时，编号优先级：

1. **首选：在原有 AC 序号末尾追加字母**（如 `AC-01-05` 后补 `AC-01-05a`）
   - 适用：补充的 AC 与现有 AC 主题相近，逻辑上属于同一组
   - 示例：AC-01-05 是"显示登录按钮"，AC-01-05a 是"点击登录按钮跳转登录页"
2. **次选：在末尾追加新序号**（如某模块原有 AC-01-01~12，补 AC-01-13）
   - 适用：补充的 AC 是新主题，与已有 AC 无强关联

**禁止**：
- ❌ 重新整体编号（会导致来源列、文档引用大面积返工）
- ❌ 多层后缀（如 `AC-01-05a-i`）
- ❌ 在中间插入并后移（如把 AC-01-05~12 全部改名）

**编号补丁示例**：

```
原始：AC-01-05 未登录显示「登录」按钮
补丁：AC-01-05a 点击「登录」跳转登录页（C01#1 类似检查点遗漏 → 补 a 后缀，主题相近）
```

每次补 AC 时必须同步更新「附录：AC 编号索引」表中的 AC 范围和数量。

## requirements-analysis.md 格式要求

<!-- agent 原文标题为 `### requirements-analysis.md 格式要求` -->

0. **（仅多文档 PRD 场景）PRD 来源溯源标记**：当需求分析基于多个 PRD md 文件时，在 analysis 顶部（RULESET_VERSION 戳下方）加来源清单，并在每个检查点标注来源文档 + 章节，便于回溯与跨文档一致性核对：

   ```markdown
   <!-- PRD_SOURCES
   - 主文档: 功能概述.md（主要功能定义，元素 ID 段 C01-C19）
   - 补充文档: 详细规则.md（业务规则细化，ID 段 BR01-BR19）
   - 参考文档: 接口定义.md（接口契约）
   -->
   ```

   检查点级溯源示例：`### C01. 搜索框（归类：8.搜索）｜需补充：否`，其检查点行注明 `来源：功能概述.md §3.2 + 详细规则.md §5.1`。单文档 PRD 不需要此标记。

1. 顶部：PRD 质量自检清单（✅/❌ 标注）
   - #1 验收标准可断言 + 断言覆盖：除了 AC 层面的检查结论外，还需附上断言覆盖的统计（元素总数、需补充数、已覆盖数）
2. 断言覆盖详情：独立章节，按通用断言库的使用流程输出完整的元素归类和检查点填充结果（格式参照 `~/.cantor-os/md/QA/common-assertion-checklist.md` 中的输出格式），直接输出完整内容，不单独生成文件、不引用外部文件
   - 🔴 **「是否需要产品补充」列只写纯文本 `是` / `否` / `—`，禁止加粗或任何 markdown 修饰**（写成 `**是**` / `` `是` `` 会被早期版本 count-coverage.py 漏计；新版已容错，但仍以纯文本为准）。
   - 🔴 **「归类」必须用通用断言库的 16 类精确名称**（如 `13.弹窗/抽屉`、`8.搜索`、`4.触发`、`15.Tab/标签页`…），16 类装不下的元素归 `BR/未归类-xxx`。**禁止自造类名**（如"二次确认弹窗""输入框""自动轮播""悬浮/展开"都不是库里的名字）。
   - 🔴 **编号 ↔ 归类必须自洽**：`C` 编号 = UI 可交互元素，其归类**必须是 16 类之一**；凡是「未归类 / 业务规则」（如 Banner 自动轮播、骨架屏加载态、纯权限可见规则）**必须用 `BR` / `U` 编号，不可占 `C` 号**。出现"C 编号 + 未归类归类"即语义错配，应改成 BR/U。（count-coverage.py 已加此校验）
   - 缺陷去重：多个"需补充=是"的检查点若指向同一问题，**合并为一个 D-xx 议题**（在缺陷汇总注明覆盖了哪些检查点），不要一检查点一缺陷导致列表虚胖。
3. 各章节诊断（每章一个表格，含状态和说明）
4. 缺陷汇总（按影响分类：用例生成/接口测试/脚本编写），断言覆盖的待补充项合并到缺陷汇总中
   - 🟢 **第四章是给下游 Agent 的技术台账**，但产品也会读：①「问题描述」「修订建议」中元素首次出现用"中文名（代号）"，**禁止裸代号开头**（`C20` → "口语诊断富文本（C20）"）；②实现/测试术语转人话（`z-index 层级`→"弹窗叠放层级"、`errRate=0`→"错误率为 0"、内部变量名/公式同理）；③「影响（用例/接口/脚本）」列标注"服务下游 Agent 排活，产品可忽略"；④缺陷表第二列是「涉及功能点（代号）」，填功能点中文名+代号，不是章节号。
5. 待确认事项汇总：断言覆盖的待产品补充项合并到此处
   - 🟢 **第五章是面向产品的自包含沟通视图**，表头：`| # | 待确认问题与需产品拍板的点 | PRD 位置 | 关联缺陷 | 等待方 | 状态 / 产品答复 |`
   - **待确认问题与需产品拍板的点**：把"问题是什么 + 要产品定什么"合并成一列纯自然语言，元素用"中文名（代号）"，**待确认（⚠️）项也必须自带问题背景与决策点**，让产品看本表即可，不必回翻第四章。
   - 🔴 **「PRD 位置」列填 PRD 功能点/章节号**（如 `§3.7 口语能力图谱 C11`、`全局交互·状态机`），指"去 PRD 哪里补"。**严禁填本分析文档的章节号（一~十）**——填本文档章节号（尤其"五"）是自指错误，无意义。`validate-requirements.py` 会对此 WARN。
   - **关联缺陷 D-xx** 降为末尾辅助字段；**状态/产品答复**：⚠️ 待确认 / ✅ 后直接写产品答复内容。
6. 分类消费指南
7. 通用提示词对接建议

## 文件写入最佳实践（强制执行）

在生成 `requirements.md` 和 `requirements-analysis.md` 等长文档时，必须遵循以下规则：

### 分段写入策略

1. **创建文件**：使用 `fs_write` 写入前 50 行以内的内容（标题、概述等），确保文件创建成功
2. **追加内容**：使用 `fs_append` 分多次追加，每次控制在 80-120 行以内
3. **禁止**：不要尝试一次性用 `fs_write` 写入超过 150 行的内容

### 避免的做法

- 不要用 PowerShell here-string (`@'...'@`) 写入多行内容——在单行命令模式下语法不兼容
- 不要用 `python -c` 内联命令写入包含中文和多层引号的长内容——转义极其复杂
- 不要在 `fs_write` 失败后反复重试相同的调用——应立即切换策略

### 失败时的应对

如果 `fs_write` 连续失败 2 次：
1. 停止重试
2. 检查是否是内容过长导致
3. 改用分段策略：先写短内容创建文件，再用 `fs_append` 追加
4. 如果 `fs_append` 也失败，使用 python 脚本文件（先用 `fs_write` 写一个短的 .py 脚本，再执行它）

### 标准流程

```
1. fs_write(path, 前50行内容)  → 创建文件
2. fs_append(path, 第51-150行) → 追加
3. fs_append(path, 第151-250行) → 追加
4. ... 重复直到完成
5. 验证文件大小和行数（用 Get-Item 检查 Length）
```

### 执行连贯性规则（强制执行）

中间步骤完成后必须立即继续下一步，不可停下来等用户催促。具体场景：
- npm install 完成后 → 立即执行依赖该包的脚本
- 文件删除完成后 → 立即执行重新生成
- sub-agent 被取消后 → 立即重试或告知用户原因并提供替代方案
- 任何工具调用成功后 → 如果还有后续步骤，立即继续

**禁止**：在中间步骤完成后只输出 "understood"/"ok" 然后停止。每轮响应必须推进到一个有意义的里程碑（文件生成完成、验证通过、或遇到需要用户输入的阻塞点）。

> 备注：本规则与 `.kiro/steering/execution-continuity.md`（always-included）等价，此处保留以与 agent 字面一致。运行时由 steering 文件主导生效。
