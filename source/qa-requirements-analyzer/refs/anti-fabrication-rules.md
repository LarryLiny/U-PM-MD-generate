# 反模式规则（不该做什么）

## 🔴 核心反模式：精确文案不得虚构

AC 表格中任何"精确文案断言"（如抽屉标题、Tooltip 文案、弹窗文案、按钮文字、时间格式、错误提示等原子字符串）**必须在 PRD 文档或原型 DEMO 源码中能找到对应字符串**。

### 来源标注格式

```
原型：HomepageConfig.tsx:203 okText: '确认切换'
PRD：5.2 节 弹窗确认 → 「确定要发布吗？」
```

### 缺源时的兜底

若 PRD/原型未定义具体文案，该检查点**只能写"应有该提示/标签"的结构性断言**（如"应展示副标题区域"），不得凭经验生造具体文字。

### 反例（必须杜绝）

```
PRD 描述：抽屉带副标题
❌ 错误 AC：标题为「发布历史 - 基础配置」
   ↑ 凭经验生造，实际原型可能是「发布历史」或别的文案

✅ 正确 AC：抽屉应展示副标题区域，副标题文案与原型一致
```

### 危害

虚构文案会把"产品实现与自己想象不一致"误报为 Bug：
- 浪费研发排查成本
- 让产品失去对需求文档的信任
- 后续用例评审时全部要返工

### 评审硬要求

所有"精确文案类" AC 在评审时**单独列表做溯源核对**，每条必须能在 PRD/原型中找到原文。

## 反模式清单

### ❌ "凭理解"归纳式扫描元素

**症状**：看几眼原型，就归纳"这有 3 个搜索框、5 个按钮"。

**问题**：会漏掉"看起来不重要"的元素：
- 搜索区中的某个筛选项
- 驱动下游逻辑的 Checkbox 组

**正确做法**：机械化逐组件扫描 `<Input>` `<Select>` `<Switch>` `<Checkbox>` `<Upload>` `<Button>` 等所有控件，先全量列出再合并。

---

### ❌ 跨模块相同功能抽象成公共章节

**症状**：A、B、C 三个 Tab 都有"发布"按钮，写一个"通用发布章节"。

**问题**：丢失模块差异：
- A 模块发布无必填校验
- B 模块发布需最少 1 条

公共章节会让用例生成器丢失这些差异。

**正确做法**：分别展开在各自模块中。

---

### ❌ 元素拆分粒度过细（流程内子按钮）

**症状**：把"编辑表单的确认按钮"和"取消按钮"作为独立元素分别归类。

**问题**：膨胀文档，重复检查点。

**正确做法**：判断"是否有独立触发场景"——
- 有独立触发场景 → 拆分（如新增按钮 vs 编辑按钮）
- 无独立触发场景 → 合并（确认/取消属于编辑流程一部分）

---

### ❌ "交互一致"模块直接引用不展开

**症状**：PRD 标"X 模块交互与 Y 一致"，分析文档就写"同 Y 模块"。

**问题**：如果 X 有任何检查点需要补充，引用会丢失这些信息。

**正确做法**：
- 所有检查点都不需要补充 → 可引用
- 任意检查点需要补充 → 必须完整展开

---

### ❌ 必填=否且未定义还推动产品补充

**症状**：检查点"是否必填=否"，PRD/原型都没定义，硬要标"需补充=是"。

**问题**：浪费产品时间，制造无意义的待确认事项。

**正确做法**："是否需要产品补充"填"—"，不建议补充。

---

### ❌ 系统级能力 PRD 未定义就标"待产品确认"

**症状**：权限矩阵、接口契约、并发竞态、性能基线、多端兼容性、安全（鉴权/越权/注入/XSS）、**UI 纯视觉样式（版式/配色/字号/图标，待出 figma）** PRD 没写，全部塞进"待产品确认"列表，或标 ❌ 拉低自检通过率。

**问题**：这几项属于系统级能力，产品不必反向推动补充；UI 纯视觉的验收是 ui-review/ui-pass 的独立下游步骤，不在本流水线断言范围。

**正确做法**：自检标 `N/A（PRD 未定义，不测试）`、按通过计入通过率（不拉低）、测试范围标"不测试"，**不标需产品补充、不列入待确认**。⚠️ UI 专项区分：只有"纯视觉长相"算 N/A；页面的**功能行为**（触发/文案/有无购买区/跳转/状态/空态）仍是业务可断言项，照测、缺则列待确认。

---

### ❌ 文档写作反模式：一次 fs_write 写超 150 行

**症状**：尝试一次性 `fs_write` 一个 365 行的 SKILL.md。

**问题**：
- PowerShell here-string 在单行命令模式下语法不兼容
- `python -c` 内联含中文 + 多层引号转义复杂
- 工具超时 / 内容截断

**正确做法**：
1. `fs_write` 前 50 行
2. `fs_append` 分多次追加，每次 80~120 行
3. `Get-Item` 验证最终大小

## 自检快速口诀

提交前问自己 6 个问题：

1. AC 里所有原子字符串都能溯源吗？
2. 我有逐组件扫描原型，还是凭印象归纳？
3. 跨模块相同功能我有分开展开吗？
4. "交互一致"的模块我有按规则决定展开/引用吗？
5. 系统级能力（权限/接口/并发/性能/多端/安全）PRD 未定义的，我标了 `N/A 不测试`（计入通过率、不标需产品补充）还是错塞进"待确认"/标了 ❌？
6. 每条 AC 断言都是**界面可观测现象 + 用户感知语**吗？有没有把白盒量（取值/ID/参数）写进功能预期（该下沉接口层），或拿字段码值（data-source=teacher）当断言主语（该翻译）？

## 启动前必查清单（来自 lessons-learned 真实踩坑）

> 以下反模式来自真实 lessons-learned（L-01~L-21）的提炼。
> 每次启动 skill 前必须扫一眼，避免重复踩坑。

### ❌ 1. 长文档一次 fs_write（来自 L-01）
症状：一次 fs_write 写超 150 行。
正确：fs_write 前 50 行 + fs_append 分批追加，每次 80~120 行。

### ❌ 2. 必跑脚本被忽略（来自 L-02，使用率 17% → 100%）
症状：脚本"提供"≠"被调用"，agent 倾向手工做更可控。
正确：完整步骤表标"必跑"的脚本必须 execute_pwsh 真跑，输出必须落盘到 analysis。

### ❌ 3. 跳过交叉检查就说"完成"（来自 L-03）
症状：阶段二写完 requirements.md 不跑 cross-check.py 直接报"阶段二完成"。
正确：阶段二交付前清单 9 项必检，cross-check exit_code=0 才算通过。

### ❌ 4. 跨文档对比靠文本相似度（来自 L-04，误报 29 项）
症状：cross-check 用 Jaccard 相似度匹配 → 误报满天飞。
正确：requirements.md AC 表格必须有"来源"列，填 `C{xx}#{n}` ID，脚本优先精确匹配。

### ❌ 5. Windows 中文乱码（来自 L-05）
症状：脚本输出中文显示为"鎶ュ憡"乱码。
正确：必须双端设 UTF-8——`[Console]::OutputEncoding = [System.Text.Encoding]::UTF8; $env:PYTHONIOENCODING='utf-8'`。

### ❌ 6. 待确认事项被动等用户问（来自 L-06）
症状：用户处理 1 项待确认后，agent 只回"已更新"，不主动报"还剩 2 项"。
正确：每轮回复必须附 `📋 待确认事项进度：已处理 X/Y，剩余 Z 项` 摘要。

### ❌ 7. fs_append 后误判任务完成（来自 L-07）
症状：写完一段 200 行表格 → 输出 "understood" → 停止。
正确：fs_append **不是里程碑**，必须连续推进直到目标文件完整。中间停顿用 `📝 写入进度` 替代 understood。

### ❌ 8. 凭记忆估算统计数字（来自 L-08，280 vs 实际 327）
症状：写"约 280 检查点"凭口算估算。
正确：数字字段必须先用 `⏳ 待 count-coverage.py` 占位 → 跑脚本 → 复制粘贴回填。

### ❌ 9. 跑了 generate-skeleton 但 fs_write 覆盖（来自 L-09）
症状：骨架太抽象 → 整段重写覆盖骨架，等于脚本白跑。
正确：跑完 generate-skeleton 必须 read_file 看骨架，用 str_replace 替换占位符。

### ❌ 10. Copy-Item 旁路绕过 fs_write 规则（来自 L-10）
症状：用 `Copy-Item` 把备份 analysis 拷到目标位置覆盖骨架。
正确：禁止任何文件复制命令（Copy-Item / cp / Move-Item）覆盖 analysis；唯一允许 3 个复用场景见 operational-rules 第 7 节。

### ❌ 11. 脚本输出只取统计数字丢弃清单（来自 L-11）
症状：跑了 extract-elements 产出 93 个元素清单，analysis 只写"扫到 93 个元素"一句话。
正确：必须列两个表格——按文件分组 + 按业务模块归类，详见 scripts-usage.md。

### ❌ 12. 用 fs_append 把章节内容追加到文件末尾导致结构错位（来自 L-13）
症状：第二节"元素归类与检查点"应该嵌入第二节内，但 fs_append 把内容追加到文件末尾（在第九节之后），章节顺序错乱。
正确：模板含 `<!-- BEGIN_ELEMENTS_AND_RULES -->` / `<!-- END_ELEMENTS_AND_RULES -->` 锚点时，必须用 **str_replace 替换锚点之间内容**，禁止 fs_append。详见 operational-rules.md 第 5.3.1/5.3.2 节。

### ❌ 13. 脚本"跑了"≠"输出完整落盘"（来自 L-14，R9 重犯）
症状：跑了 cross-check / validate-requirements，看到 exit_code=0 + 摘要打印就过了，但**报告内容没写入 analysis 对应章节**。
正确：脚本跑通（exit_code=0）只是必要条件。脚本完整输出（执行过程、明细、统计）必须落盘到 analysis 对应章节：
- `cross-check.py` 报告 → analysis 第十节"交叉检查结果"
- `validate-requirements.py` 9 项 check → analysis 第三节 3.2
- `count-coverage.py` 数字 → analysis 第八节

**验证方式**：脚本跑完后用 grep analysis 确认章节内容存在。仅看终端摘要不算消费。

### ❌ 14. 原型展示要素未归位到检查点（来自 U5 首页 sales-xlsx 对比）

**症状**：原型代码有"共 N 本教程"、空状态文案、动态数据展示等元素，但 analysis 既没挂到现有 C/BR 检查点，也没作为新 BR 列出。下游用例生成时这些测试点被遗漏。

**先做分类筛选**——决定是否纳入测试：

| 展示要素类型 | 是否纳入测试 |
|------------|-------------|
| 文案（toast、空状态、标题、说明文字） | ✅ 纳入 |
| 状态展示（标签文字、徽章数字、loading 提示）| ✅ 纳入 |
| 动态数据展示（总数、计数、时间）| ✅ 纳入 |
| **视觉规范（颜色、字号、间距、动画曲线）**| ❌ **默认不纳入**——以设计师方案为准；仅当 PRD 明确定义具体值时纳入 |

**纳入后的归位流程**（按优先级）：

1. **优先关联到现有检查点**——遍历现有 C/BR 的所有检查点，找最相关的一条
   - "总数展示" → `C{容器}#1` 数据正确加载并展示
   - "空状态文案" → `C{容器/弹窗}#2` 内容正确加载并展示
   - "toast 文案" → `C{触发元素}#1` 点击后状态变更
   - "标签文字" → `C{容器}#1` 数据正确加载并展示
2. **关联不上才新增 BR**——独立的、跨多个元素的、不属于任何元素细节的全局规则

**正确做法**：

```
跑完 extract-elements.py 后，必须额外通读关键 tsx 文件提取静态展示文案：
- 容器组件（书架/弹窗/列表的根 tsx）
- 空状态/错误态条件渲染段（如 `{xxx.length === 0 ? ... : ...}`）

提取规则：
- 中文字符串字面量（如 '共 N 本教程'、'所有教程已领取完毕'）
- 由 props/state 拼接的动态文案（如 `共 {n} 本教程`）

提取后按上述分类筛选 + 归位流程处理。
```

**禁止**：
- ❌ 在通用断言库（16 类）中新增"文案/颜色"细项（污染清单）
- ❌ 见到原型有的就新增 BR（先尝试挂到已有检查点）
- ❌ 把视觉规范（颜色/字号/间距）写入测试（除非 PRD 明确定义）
- ❌ 因为"PRD 没说"就跳过原型实现的**功能性**展示要素（违反 anti-fabrication）

**实测代价**：U5 首页第一轮生成 105 条用例后，对比手写销售流程用例发现遗漏 2 条原型有但 analysis 漏的功能性测试点（"共 N 本教程"展示 + "所有教程已领取完毕"空状态）。原因是 extract-elements.py 只扫交互元素不扫展示型文本节点，agent 也没补充通读原型 tsx 的步骤。

### ❌ 15. 三套脚本 PASS 误当流程完整（来自 L-18，PRD 增量更新 Step 3.5 漏跑）

**症状**：count-coverage / cross-check / validate 三套脚本全绿后直接交付，漏掉只在 ref 里规定的"非脚本守门"步骤——典型是 PRD 增量更新的 Step 3.5「测试驱动的 PRD 缺陷修正计数」（手工统计 + 维护哨兵 `PRD_DEFECT_TOTAL`），凭 SKILL.md 摘要 + 记忆走流程，没 readFile operational-rules.md §7 全文，因此漏跑。

**问题**：这类步骤嵌在 ref 的"展开层"（含具体规则、表格、哨兵格式），SKILL.md 标题层只露概括；脚本守门覆盖不到 → 长对话场景大概率漏。

**正确做法**：

1. **涉及流程类剧本**（PRD 增量、阶段交付清单、上下文恢复等），动手前先 `readFile / Get-Content` 完整重读对应 ref 章节，不依赖 SKILL.md 摘要、不依赖记忆。
2. **三套脚本 PASS ≠ 完成**：补一道"非脚本步骤盘点"——grep ref 找出 `必跑/强制/⚠️/🔴` 标记逐项核对，缺一不算完成。
3. **每个流程都有自己的哨兵**（如 `PRD_DEFECT_TOTAL`、`<!-- BEGIN_*_RULES -->`），交付前 grep 确认存在 = 流程跑全的最小证据。
4. PRD 增量更新已由 `validate-requirements.py` 第 12 项 check（PRD 缺陷修正追踪一致性）守门——但**它只在带 `--analysis` 时触发**，仍需主动跑。

**反例**：

> LLM：我跑完 cross-check 100% / validate PASS，PRD 增量更新完成 ✅
> 用户：skill 里应该有测试驱动 PRD 修改点的统计，你跑到了吗？
> LLM：…没跑到。（实际缺章节 + 哨兵；下游 qa-test-report 读不到累计数）

### ❌ 16. 断言用模糊词蒙混（"正确/正常"非具体值）

**症状**：AC 断言列写「提示正确」「排序正常」「展示符合预期」「交互友好」——非空、>5 字、不是 TODO 占位符，`validate` check 7 全过；但到了写 playwright 脚本 `expect(X).toBe(?)` 时才发现"正确""正常"填不出具体值。本该分析阶段抓到的模糊点，拖到了脚本阶段才暴露。

**问题**：模糊形容词不是可断言的具体值。它掩盖了"PRD 其实没定义这个点"的事实——脚本阶段才被迫面对，返工成本高。

**正确做法（断言化试金石）**：

1. 填每个**必填**检查点 / AC 断言时先自问"能写成 `expect(具体可观测).toBe(具体值)` 吗"。
2. **具体值** = 引号文案 /「数字」/ 路由 / 枚举 / 布尔 / 可见·隐藏 / 启用·禁用 等可观测态；**模糊词**（正确/正常/符合预期/符合要求/无误/友好/合理/适当/恰当/清晰/流畅/良好/准确）不算。
3. 填不出具体值 → **就地标缺口**（必填→需补充=是 / D-xx；非必填→`—`），不许用模糊词凑数。
4. 脚本兜底：`validate-requirements.py` check 15「断言具体性」对纯模糊词断言 WARN；`count-coverage.py` 的 `empty_required_content` 抓必填检查点内容空。

**反例 → 正例**：

> ❌ 「排序正常」 → ✅ 「列表按 创建时间 倒序，最新在首行」（填不出排序规则就标 D-xx 待产品确认）
> ❌ 「提示正确」 → ✅ 「toast 文案为「保存成功」」
> ❌ 「跳转符合预期」 → ✅ 「跳转到 `/login`」

**来源**：用 skill 编写脚本时发现"本该分析阶段抓到的模糊点留到脚本阶段"+"方法盲区只能靠断言化暴露"（2026-06）。

### ❌ 17. UI 纯视觉样式错列为缺陷/待确认（来自 L-19）

**症状**：PRD 的状态页/页面写"样式由设计师决定 / 待出 figma"，analysis 把"具体视觉样式"既标"非断言项（—）"、又生成 D-xx 缺陷 + 塞进待确认（⚠️）+ 记"影响脚本编写"——自相矛盾，且把视觉验收当成卡本流水线的阻塞项。

**问题**：UI 纯视觉的验收是 ui-review / figma-r / ui-pass 的**独立下游步骤**，不在本流水线断言范围，不影响功能用例/功能脚本。视觉缺失归因到"影响脚本编写"也是错的（视觉脚本归 pixel-diff/ui-review，不是本流水线的功能脚本）。

**正确做法**：拆检查点先分两类——
- **功能行为**（触发/文案/有无购买区/跳转/状态切换/空态是否展示）= 业务可断言项，照测、缺则列待确认；
- **纯视觉样式**（版式/配色/字号/间距/图标/动效）= figma 未出时按系统级 N/A，**不缺陷、不待确认、不标需补充=是**，视觉验收交 ui-pass。
- 判据：缺"功能行为定义"→缺陷；缺"视觉长相/出图"→N/A。详见 [prd-quality-checklist.md#系统级能力项处理规则强制](prd-quality-checklist.md) 的「UI 视觉样式专项边界」。

**反模式**：
- ❌ 把"样式待出 figma"当 ⚠️ 待确认
- ❌ 同一检查点既标"—"又生成缺陷
- ❌ 反向一刀切：把页面功能行为也跟着视觉划 N/A（功能行为必须照测）

**来源**：商品可售范围控制 7022520795 阶段一复盘（2026-06-29）。

### ❌ 18. 测试层级混淆——白盒量写进黑盒功能预期（来自 L-20）

**症状**：把"字段取值口径""各端登录态怎么取""空值 vs 标识判定""跳转参数含 ID""是否调了某接口"等**界面看不见的系统内部量**写进功能层的前置/预期，造出预置条件与预期都不可观测、测试员无法判断通过与否的用例。还常因为"取值/ID 校验有价值"就把它留在功能待确认里当阻塞。

**问题**：功能测试是黑盒，测试员手里只有界面。取值/ID/参数校验有价值，但价值在**接口测试层**；本需求接口 N/A 时，它根本不该卡功能流水线。

**正确做法（按测试类型分流）**：
- 功能层只断言**可观测现象**（跳对页面、页面内容确属该对象、列表只出该见项、文案/状态正确），前置态写成**可构造**的（如"用一个'暂无院校'测试账号"）；
- 取值/参数/ID/是否调接口 → **下沉接口测试层**，登记到「接口测试消费顺序」；
- 接口测试 N/A → 这些白盒项**不在功能流水线作阻塞待确认**。
- 判据：**界面看得见→功能层断言；看不见→接口层（接口 N/A 则不阻塞）**。详见 [assertion-coverage-checklist.md](assertion-coverage-checklist.md) 可测性三问后的「白盒越界识别」。

**来源**：商品可售范围控制 7022520795 第五章待确认#2 复盘（2026-06-29）。

### ❌ 19. 实现术语泄漏——字段名/码值当预期主语（来自 L-21）

**症状**：把需求文档/字段定义里的数据契约语言（`data-source=teacher`、`type=library/custom`、`skill=listening`、`progress`、枚举码值）原样搬进预期结果。现象其实界面看得见（有「老师布置」标识、「听力」标签），但用错了语言——功能测试员/验收方只认界面文字，读到码值困惑、无法对照判定。

**与白盒越界（#18）的区别**：#18 是界面**看不见**的内部量（取值/ID/参数）→ 下沉接口层；本条是界面**看得见**但写成了码值 → 做术语翻译。

**正确做法（术语翻译）**：
- 预期结果的**主语只能是用户能看见/能操作的现象**（"显示「老师布置」标识""归到「听力」分类"）；
- 字段名/码值最多作**括号补充**或挪到**来源/备注列**，不作预期主语；
- 码值在界面无可视表征 → 回到 #18 白盒越界分流（下沉接口层）。
- 一句话：可观测但用错语言→翻译成用户感知语；不可观测→下沉接口层。详见 [assertion-coverage-checklist.md](assertion-coverage-checklist.md) 「实现术语泄漏」。

**来源**：他人跑 skill 时预期结果直接搬字段定义（2026-06-29）。

### ❌ 20. 漏打 token 埋点（来自 L-22）

**症状**：跑测试 skill（分析/用例/自动化/报告）整条流程，产物脚本全绿交付，却一个 `cantor qa-token-mark` 都没打——没 `_baseline`、没阶段点、没 `qa-token-flush`。埋点段在 SKILL.md 末尾、非脚本门禁，开工"脚本调用计划"又没列它 → 整轮漏。

**问题**：本次运行 token 明细**永久丢失、无法事后补**（Kiro 源靠 _baseline 锚定的相邻 mark 增量；开工没打基线 + 中途没打点 = 阶段无从切分，事后补只得 12h 混合噪声）。fail-silent 只保证不阻断，不替你记得打。

**正确做法**：
- **启动测试 skill 第一件事**（"脚本调用计划"Step 0，与必跑脚本并列）：`cantor qa-token-mark --skill <name> --phase _baseline --action start --feature "<需求名>"`
- 每跨阶段边界打点；交付前清单最后一项 `cantor qa-token-flush` 兜底。
- 详见 `_lib/token-metering.md` 强制铁律 + operational-rules §5.1 / 交付清单。

**来源**：商品可售范围控制 7022520795 真重跑漏打（2026-06-30）。
