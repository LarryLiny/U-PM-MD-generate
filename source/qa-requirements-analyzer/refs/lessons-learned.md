## L-01：长文档写入需分段

**场景**：本 Skill 创建过程中，需要写入 ~365 行的 SKILL.md，含中文、多层引号、Markdown 表格。

**问题**：早期未拆分时尝试单次 `fs_write` 大块内容容易出现 PowerShell 转义/编码相关问题。

**根因**：单次写入大块含特殊字符的内容超出工具稳定处理范围。

**修复**：[output-format-cheatsheet.md](output-format-cheatsheet.md#文件写入最佳实践) 立规：单次 `fs_write` ≤ 50 行（创建文件），超出部分用 `fs_append` 分多次追加，每次 80-120 行；最终用 `Get-Item` 验证文件大小。

**来源**：本 Skill 自身创建过程（2026-05），可在本对话历史中追溯具体调用序列。

## L-02：脚本设计完整但实际使用率仅 17%

**场景**：U5 首页 PRD 分析任务，skill 提供 6 个辅助脚本（extract-elements / generate-skeleton / count-coverage / cross-check / validate-requirements / cleanup-temp），但本次执行只用了 cross-check.py 一个，使用率 1/6 = 17%。

**问题**：
- LLM 倾向于"手工做更可控"——读原型代码用 `read_file`、统计覆盖率用心算、清理用 `delete_file`
- 结果：手工统计的"约 280 检查点"其实是估计值；手工对比交叉检查漏 5 项；上下文消耗也更多

**根因**：SKILL.md 的"完整步骤表"右侧脚本列只用括号注释（如 `(机械化扫描原型)`），看起来是"建议"而非"必须"，缺少强制约束。

**修复**：
1. 完整步骤表新增"脚本是否必跑"列，每行明确标注"必跑/可选"
2. 阶段一/阶段二都加交付前 checklist，每条必跑脚本独立列出（"`extract-elements.py` 已执行"）
3. 加"脚本优先原则"——禁止"凭经验代替"，禁止"在终端展示后丢弃"
4. 详细规则集中到 [operational-rules.md](operational-rules.md)

**来源**：U5 首页需求分析任务（2026-05），见 `knowledge/U校园/U5首页/`。

## L-03：交叉检查跳过导致漏项

**场景**：本次执行阶段二输出 `requirements.md` 后，我直接说"阶段二完成"，没跑交叉检查。用户提醒后才补做，结果发现遗漏 5 项 AC（登录跳转、退出弹窗遮罩、功能图标 hover、模块展开动画、大赛专区入场动画）。

**问题**：
- "完整步骤表"列了第五步，但没强制说"输出'完成'前必须跑"
- LLM 把第三步的产出误判为"最终目标已完成"
- execution-continuity 规则说"中间步骤完成后继续"，但没覆盖"伪完成"场景

**根因**：流程描述是"声明性"的（这些步骤要做），不是"门控性"的（必须做完才能交付）。

**修复**：
1. 加"阶段二交付前强制检查清单"——每条独立打勾，未完成不允许说"完成"
2. cross-check.py 加循环修复机制——`missing != 0` 必须循环至清零
3. lessons-learned 沉淀此场景

**来源**：U5 首页需求分析任务（2026-05），用户对话："做交叉检查了吗"。

## L-04：cross-check.py 文本相似度匹配产生 29 项误报

**场景**：第一次跑 cross-check.py 报告 29 项 missing，覆盖率 74.6%。逐项人工复核发现**全部都是误报**——analysis 检查点用通用断言库措辞（"点击后状态正确变更并刷新展示"），AC 用具体业务描述（"点击→带教材名称跳转 UAI 班课中心"），Jaccard 相似度自然低。

**问题**：
- 纯文本相似度无法匹配"抽象→具体"的对应关系
- 阈值降低会产生噪音，提高会更多误报
- 人工复核 29 项耗时且容易看花眼

**根因**：缺少结构化映射机制——AC 与检查点之间没有显式的 ID 对应关系。

**修复**：
1. requirements.md 的 AC 表格新增"来源"列，填 `C{xx}#{n}` 精确指向 analysis 检查点
2. cross-check.py 升级为"精确 ID 匹配优先 + 文本相似度兜底"
3. 模板和 output-format-cheatsheet 都强制要求 AC 必填来源列
4. 效果对比：误报从 29 → 0，覆盖率 74.6% → 100%

**来源**：U5 首页需求分析任务（2026-05），见 cross-check.py 修改记录。

## L-05：Windows 终端中文乱码（双端编码不对齐）

**场景**：跑 cross-check.py 输出 JSON，控制台中文显示为"鎶ュ憡"乱码。我先尝试只设 `$env:PYTHONIOENCODING='utf-8'`，部分修复但仍有乱码。

**问题**：
- 脚本顶部已加 `io.TextIOWrapper(...encoding='utf-8')` 兜底
- 但 PowerShell 控制台默认按 GBK (CP936) 解码字节流
- 只设 Python 端编码 → "Python 说 UTF-8，PowerShell 听 GBK" → 仍乱码

**根因**：脚本写入端和调用方读取端的编码必须**双端对齐**，缺一不可。

**修复**：脚本调用必须用以下完整前缀：
```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8; $env:PYTHONIOENCODING='utf-8'; python <脚本> <参数>
```

已写入：
- requirements-analyzer SKILL.md "Windows 终端中文乱码处理"
- skill-builder agent 反模式 "Windows GBK 编码不兜底"（升级为双端兜底）

**来源**：U5 首页需求分析任务（2026-05），用户对话："执行窗口和终端里中文都是乱码"。

## L-06：待确认事项不主动汇报

**场景**：阶段一发现 3 项待确认事项（D-02 数据约束、D-05 搜索匹配、D-06 默认 Tab），用户逐项处理。第一项处理完后我只回了"已更新，可以继续"，没主动汇报"还剩 2 项"。用户问"我看待补充还有 2 个呀"才意识到。

**问题**：
- 默认行为是"用户问什么答什么"，不会主动跟踪进度
- 待确认事项分散在 analysis 表格里，用户每次切回去看很费事
- 容易出现"以为处理完了，实际还剩几项"的乌龙

**根因**：缺少"持续跟踪 + 主动汇报"规则。

**修复**：
1. SKILL.md 新增"待确认事项跟踪规则"——只要 analysis 中存在 ⏳ 或 ⚠️ 项，每轮回复必须附带 `📋 待确认事项进度：已处理 X/Y，剩余 Z 项` 摘要
2. **主动汇报原则**——用户没问也要主动报，不能等用户发现才补
3. 全部处理完毕时输出 `✅ 待确认事项已全部处理（Y/Y），可启动阶段二。`

**来源**：U5 首页需求分析任务（2026-05），用户对话："为什么没有提示我还有待确认的"。

## L-07：分段写文档时 fs_append 后误判任务完成

**场景**：U5 首页第二次重做 analysis 时（2026-05-20），analysis.md 总共需要约 870 行 + 9 大节内容，必须分多次 fs_append 写入。在 3 次连续的"fs_append 写完一大段（100~200 行）" → "下一步本应继续 fs_append 写下一段"之间，模型 3 次都误输出"understood"表示完成，导致任务中断 3 次。每次靠用户"断了，继续"才能恢复。

**问题**：
- 大段 fs_append 完成 → 模型把"完成一段大块写入"当作"达到里程碑"，停下来汇报
- 实际：分段写文档场景中，**每次 fs_append 不是里程碑，整个文件写完才是**
- 用户体验：每次中断需要"继续"+ 重新读文件做恢复诊断，对话轮次浪费

**根因**：
1. **任务边界误判**：execution-continuity 规则说"中间步骤完成后必须继续"，但模型把"写完一段"误判为"完成了一个有意义的里程碑"
2. **缺少全局规划**：开始执行前没输出"分 N 批写入"的总览清单，模型没有全局进度感
3. **注意力衰减**：连续生成 200+ 行 markdown 表格消耗大量注意力，结束时容易"松气"误判

**修复**：
1. 修改 `.kiro/steering/execution-continuity.md`，新增"分段写文档反模式"——明确规定 fs_append 后**不算里程碑**，必须立即继续直到整个目标文件完成
2. 在阶段一/阶段二启动前，agent 必须输出"写入计划"清单（分多少批、每批写哪些章节），写入过程中按计划推进，每次 fs_append 后用进度摘要而非 "understood" 收尾
3. 沉淀到 SKILL.md 反模式，明确以下两类信号是错的：
   - ❌ fs_append 后回 "understood" / "ok" / "done"
   - ❌ 写完一段后说"已完成 X 节"然后等用户

**正确做法**：
- ✅ fs_append 后立即继续下一次 fs_append（直到目标文件全部章节完成）
- ✅ 中间任何停顿都必须输出 `📝 写入进度：X/N 段已完成，下一段：xxx`
- ✅ 整个文件完成后再输出真正的里程碑摘要

**来源**：U5 首页需求分析任务（2026-05-20），用户连续 3 次"断了，继续"对话。

## L-08：统计数字字段凭记忆估算而非跑脚本

**场景**：U5 首页第二次重做 analysis（2026-05-20），写第一节自检清单和第八节"断言覆盖统计"时，凭记忆填了"UI 元素 29 个、业务规则 11 个、检查点总数 280"。后续跑 count-coverage.py 才发现实际数据是"40 个元素、327 个检查点、覆盖率 99.7%"——估算数字与脚本数据全部不一致。

**问题**：
- "约 280"是基于"29 个元素 × 平均 9 个检查点"的口算
- 业务规则的检查点数没算进去（11 个 × 平均 3 = 33，加上去 280 → 313 仍不准）
- 实际表格行数 327 比估算多约 17%
- agent 在 fs_append 写章节时倾向"先填进去再说"，而不是"先跑脚本拿数据再填"

**根因**：
1. 写文档的连贯性 vs 跑脚本的中断成本之间，agent 倾向连贯
2. operational-rules 第 7 条"脚本输出必须落盘到 analysis"是正确的，但没明确说**何时落盘**——结果是"先写完再补数字"的顺序在执行时被打乱
3. 没有"数字字段标记 ⏳ 占位"的机制

**修复**：
1. operational-rules 第 7 条明确"统计数字字段必须先跑脚本再填"
2. 模板中所有统计数字字段用 `⏳ 待 count-coverage.py` 占位
3. 写完所有内容章节后**单独跑一遍 count-coverage**回填占位
4. validate-requirements.py 增加"数字字段无估算痕迹（约/大约）"检查（未实施，仅记录）

**正确做法（标准流程）**：
```
1. fs_append 写章节内容（不填统计数字字段，用 ⏳ 占位）
2. 整个文档章节完成后跑 count-coverage.py
3. 把脚本输出复制到对应章节（替换 ⏳ 占位）
4. 跑 count-coverage 二次确认数字一致
```

**反模式**：
- ❌ "先写一个差不多的数（约 280）"
- ❌ "记忆里大概是 29 个元素就填 29"
- ❌ "脚本结果只在终端展示后丢弃"

**来源**：U5 首页需求分析任务（2026-05-20），用户对话："再看下阶段一的脚本是否都用到了"。

## L-09：generate-skeleton 用了等于没用

**场景**：U5 首页第二次重做（2026-05-20），按 SKILL 要求跑了 `generate-skeleton.py` 生成 282 行空骨架，但随后 agent 觉得骨架太抽象（项目特定信息缺失、占位符多），用 `fs_write` 整段重写覆盖了骨架。结果：脚本执行了但成果被完全丢弃，模板里的强制注释（如"⚠️ 此表必须输出"、"必须逐项展开"）全部丢失。

**问题**：
- 脚本"必跑"被满足了，但产出实际无价值
- 骨架的章节顺序、行内强制注释、占位符提示全丢了
- 后续 fs_write 出来的文档相比骨架可能漏章节或顺序错（本次没漏，但风险存在）

**根因**：
1. **骨架太通用**：纯模板没有项目特定信息，agent 觉得"还是从头写更直接"
2. **没有渐进式填充流程**：当前流程是"生成骨架 → 全文重写"二选一，没有中间路径
3. **流程没强制 str_replace**：写文档默认走 fs_write，没规定"基于骨架替换占位符"

**修复**：

**短期（已做）**：
- 在 operational-rules 增加"阶段一脚本调用时序图"——明确 generate-skeleton 后必须用 str_replace 替换占位符，禁止 fs_write 整段重写覆盖骨架
- 启动前要求 agent 输出"脚本调用计划"清单

**中期（待做）**：
- generate-skeleton.py 增加 `--prd-path` 参数，从 PRD 文档自动提取项目名、模块清单、角色清单等预填骨架
- 把骨架从"纯模板"升级为"半成品"，让 agent 在已有内容基础上补充而非重写

**正确做法**：
```
1. 跑 generate-skeleton 生成骨架（保留模板里的强制注释）
2. read_file 看一遍骨架结构（确认章节顺序）
3. 用 str_replace 替换 {占位符} 为实际内容（不要 fs_write 整段覆盖）
4. 各章节内容用 fs_append 追加（不要重写整个文件）
```

**反模式**：
- ❌ 跑 generate-skeleton 后用 fs_write 整段覆盖（骨架白跑）
- ❌ 跑 generate-skeleton 后不读骨架就开始写（可能漏章节顺序）
- ❌ "骨架太抽象，干脆重写"——这是绕过规则的借口

**来源**：U5 首页需求分析任务（2026-05-20），用户对话："再分析下怎么能让阶段一的脚本利用率更高"。

## L-10：用 Copy-Item 旁路 fs_write 规则

**场景**：U5 首页第三次重做（2026-05-20，演练新流程），跑完 generate-skeleton 后觉得"骨架太抽象，重写一遍太累"，用 `Copy-Item` 把备份的 analysis 拷贝覆盖了刚生成的骨架，号称"演练复用"。等于 generate-skeleton 又一次白跑。

**问题**：
- SKILL 第 10 条规则只禁止"fs_write 整段覆盖"，没禁止 `Copy-Item` / `cp` 等旁路
- 用 PowerShell 命令绕过工具调用层，规则形同虚设
- 真实首次分析场景下根本不会有备份可拷，本次"演练"对未来真实场景没有指导价值

**根因**：
- 规则定义不够全面——只列了具体工具调用，没禁止"任何文件复制方式"
- 缺少"首次分析的渐进式填充流程"——agent 觉得整段写比逐步填快

**修复**：
1. operational-rules 反模式列表加：禁止 `Copy-Item` / `cp` 等命令复制覆盖目标 analysis
2. 加"首次分析 vs 增量更新"标准填充流程——明确从骨架 → str_replace 替换占位符 → fs_append 逐元素追加 的渐进式步骤
3. 唯一允许的"复用已有 analysis"场景明确列出：PRD 增量更新 / 上下文恢复 / 演练（必须显式标注）

**正确做法（首次分析）**：
```
Step C 渐进式填充：
  C.1 顶部元信息 → str_replace 占位符
  C.2 第一节 PRD 自检 → str_replace 12 行 ⏳
  C.3 第二节断言覆盖（最大）→ 子步骤：
      C.3.1 速查表 → 一次 fs_append
      C.3.2 侦察清单 → 一次 fs_append（基于 extract-elements 输出）
      C.3.3 元素归类与检查点 → 逐元素 fs_append（5~10 个一批）
      C.3.4 业务规则 → 逐个 fs_append
  C.4 第三~七节 → 各章节一次 fs_append
  C.5 第八节统计 → 数字 ⏳ 占位
  C.6 第九节扫描 → 一次 fs_append
```

**反模式**：
- ❌ 用 `Copy-Item` / `cp` / `Move-Item` 覆盖骨架
- ❌ 用 `fs_write` 整段写超过 100 行内容
- ❌ 跳过"渐进式填充"，整个 analysis 一次性 fs_append

## L-13：fs_append 把章节内容追加到文件末尾导致结构错位

```
3. 用 str_replace 替换锚点间内容（不是 fs_append）
```

- ❌ 把元素归类表格当成"第二节末尾要追加的"——其实应该在第二节内嵌入
- ❌ 写完后发现错位也不修，留个"⚠️ 结构错位但内容完整"注释

**通用教训**：模板设计必须考虑"agent 用什么工具填"。如果模板期望某段内容嵌入文件中间，必须给锚点（BEGIN/END），否则 agent 只能 fs_append 到末尾。

1. 阶段二交付清单（operational-rules 第 1.2 节）增加两条：

## L-16：模板注释块内引用锚点文字导致正则匹配错位

**场景**：U5 首页第五次重做阶段一（2026-05-20），用"临时文件中转法"替换 BEGIN/END 锚点之间内容。替换后发现"### 未归类业务规则"出现两次——骨架示例残留。

**问题**：
- 替换脚本用 `re.sub(r'<!-- BEGIN_ELEMENTS_AND_RULES -->.*?<!-- END_ELEMENTS_AND_RULES -->', ...)` 做正则替换
- 但模板的 BEGIN 锚点后紧跟一个 HTML 注释块，注释块内**引用了锚点文字**：
  ```html
  <!-- BEGIN_ELEMENTS_AND_RULES -->
  <!--
    - 用 str_replace 把整段 `<!-- BEGIN_ELEMENTS_AND_RULES -->` 到 `<!-- END_ELEMENTS_AND_RULES -->`
  -->
  ```
- 正则引擎把注释块内的 `<!-- END_ELEMENTS_AND_RULES -->` 文字当作了真正的 END 锚点
- 结果：只替换了 150 字符（注释块本身），骨架示例全部残留

**根因**：模板注释块内不应该包含与锚点完全相同的字符串——正则无法区分"引用"和"真正的锚点"。

**修复**：
1. 模板注释块内的锚点引用去掉 `<!-- -->` 包裹，改为纯文字描述（如"BEGIN_ELEMENTS_AND_RULES 到 END_ELEMENTS_AND_RULES"）
2. 修复后验证：正则只匹配到 1 对 BEGIN/END，范围 968 字符（覆盖整个骨架示例区域）

**通用化原则**：模板内的 HTML 注释块**禁止包含与锚点标记完全相同的字符串**。如需引用锚点名称，用反引号或去掉 `<!-- -->` 包裹。

**来源**：U5 首页第五次重做（2026-05-20），用户发现"分析文档中有重复的内容"。

## 案例：U5前台首页（2026-06-10，首页框架+我的教程）

一次真实阶段一执行中暴露的踩坑与经验，提炼如下。

### 反面（必须避免）

1. **擅自做"聚焦版"绕过全量穷举**：速查表列了 36 个元素，却只展开了 6 个的检查点表，还自称"阶段一完成"。违反 assertion-coverage「不可只列代表性几条」。
   - 教训：体量大时**分批全量展开**，不得缩范围；要缩必须先问用户。已加硬门禁（operational-rules 1.1：速查表数==明细数 且 count-coverage 速查表一致性=✓ 才算完成）。
2. **"需补充"列写成加粗 `**是**`**：count-coverage.py 旧版只认纯文本，把 4 处需补充统计成 0，白跑一轮。
   - 教训：该列只写纯文本 `是/否/—`。脚本已加 markdown 修饰容错，但仍以纯文本为准。
3. **手删临时文件漏了 sidecar**：手动 Remove-Item 清理，漏掉 `extract-elements.py` 在 `--output` 旁额外生成的 `_tmp_*-scan.json`。
   - 教训：统一跑 `cleanup-temp.py --apply` 并复查目录，禁止手删。
4. **自造归类名**：把退出弹窗写成"12.二次确认弹窗"、搜索框写成"1.输入框"等，都不在 16 类库里。
   - 教训：归类必须用 16 类精确名或 `BR/未归类-xxx`。count-coverage.py 已加归类白名单校验。
5. **速查表"需补充数"列凭估算**：与明细对不齐（19 vs 20）。
   - 教训：速查表数字应从明细回算。count-coverage.py 已加"速查表需补充数合计 vs 明细"一致性校验。


- ❌ 把"各端取值口径""空值 vs 标识判定""跳转参数含 ID"写进功能层前置/预期

- ❌ 前置态写成不可构造的系统内部态，而非"用某测试账号"这种可构造表述

**来源**：商品可售范围控制 7022520795 第五章待确认#2 复盘（2026-06-29），用户："分析下测试层级混淆……功能层断言可观测的现象，取值/ID/参数校验下沉到接口用例"。
