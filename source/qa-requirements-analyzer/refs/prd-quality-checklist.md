# 第一步：PRD 质量自检

使用以下 12 项清单逐项检查 PRD：

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 验收标准可断言 + 断言覆盖 | 每条 AC 有正向+反向断言，有数值约束的有边界值；同时按通用断言库（`~/.cantor-os/md/QA/common-assertion-checklist.md`）侦察所有元素并归类，检查必填检查点是否有 PRD 定义，未定义的标记为缺陷。列表/详情/图表类元素须下钻字段级核对数据规则定义（见通用断言库 7#13/16#9）。**每个必填检查点过「断言化试金石」**：填不出 `expect(X).toBe(具体值)`（只有"正常/正确/符合预期"等模糊词）即视同未定义→标缺口。**详细执行流程见 [assertion-coverage-checklist.md](assertion-coverage-checklist.md)** |
| 2 | 状态机完整 | 所有状态转换列出，含异常路径，有 YAML 格式 |
| 3 | 已知 Bug 标记 | Bug 行为/期望行为分离，标记 xfail |
| 4 | 数据约束精确 | 精确到字节/类型/边界，包含/不包含边界明确 |
| 5 | 权限矩阵完整 | 所有角色×操作定义，无权限 UI 表现已定义 |
| 6 | 接口契约完整 | 请求/响应结构完整，错误码枚举完整 |
| 7 | 前置条件链完整 | AI 可据此到达每个测试起点，有代号可引用 |
| 8 | 并发竞态有断言 | 每个竞态场景有具体可断言的标准 |
| 9 | 性能基线有数值 | 有具体数值和测量起止点 |
| 10 | 多端适配明确 | 支持/不支持都明确 |
| 11 | 特殊字符已定义 | 多语言/符号/Emoji 行为已定义 |
| 12 | 业务实体结构完整 | 所有业务实体有结构化输出定义 |

输出：在 `requirements-analysis.md` 顶部生成自检结果表，每项标注 ✅ 或 ❌。

> **系统级能力项的特殊处理（#5 权限矩阵 / #6 接口契约 / #8 并发竞态 / #9 性能基线 / #10 多端适配 / 安全）**：PRD 未定义时**不标 ❌**，而是标 **`N/A（PRD 未定义，不测试）`**，并**按通过计入通过率**（不因这些系统级项 PRD 没写而拉低通过率）。详见下方「通过率门槛」与「系统级能力项处理规则」。

## 通过率门槛

- 自检通过率 ≥ 80%（10/12 项通过）才可输出需求规范
- **通过率计算**：`通过率 =（✅ 通过项 + N/A 不测试项）/ 12`——系统级能力项（权限/接口/并发/性能/多端/安全/UI 纯视觉样式）PRD 未定义时记 `N/A`，计入分子，**不拉低通过率**。
- 未通过的项（真正的 ❌，如验收标准可断言、数据约束、特殊字符行为等业务级项缺失）必须在分析报告中给出修订建议

## 系统级能力项处理规则（强制）

> 适用项：**权限矩阵、接口契约、并发竞态、性能基线、多端适配、安全（鉴权/越权/注入/XSS 等安全相关检查点）、UI 纯视觉样式/出图（版式/配色/字号/间距/图标等"长什么样"，视觉验收归 ui-review / figma-r / ui-pass 独立步骤）**。

这些属于**系统级能力**，产品通常不在功能 PRD 里逐条定义，测试也不必反向推动产品补充。当 PRD/原型对某项**未定义**时：

1. 自检结果标 **`N/A（PRD 未定义，不测试）`**，**不标 ❌**，**按通过计入通过率**。
2. 在「测试范围 / 对应章节」标注 **"不测试（PRD 未定义）"**。
3. **不列入「待确认事项汇总」、不在断言覆盖里标"需产品补充=是"、不生成"待产品确认"类缺陷**。
4. 例外：PRD **确有**定义（如明确写了角色×操作、错误码、并发策略、性能数值、安全要求）→ 正常按 ✅/❌ 评估并测试。

> **UI 视觉样式专项边界（强制区分，勿一刀切）**：一个页面/状态页拆出的检查点要分两类——
> - **功能行为**（触发条件、提示文案、有无购买区/入口、跳转目标、状态切换、空态是否展示等）= **业务可断言项**，PRD 缺失按业务级 ❌ 处理、该测照测、缺则列待确认；
> - **纯视觉样式**（版式/配色/字号/间距/图标/动效等"长什么样"）= 按本规则 **N/A**：figma 未出时视觉验收交给 ui-review / figma-r / ui-pass 这一**独立下游步骤**，不在本测试流水线断言范围，**不影响用例/功能脚本**，故不标"需补充=是"、不生成缺陷、不列入待确认。
> - **判据一句话**：缺的是"功能行为定义"→业务级缺陷；缺的是"视觉长相/出图"→视觉 N/A。典型场景：越权缺省页"样式由设计师决定/待出 figma"——其触发/文案/无购买区照测，唯"具体视觉样式"标 N/A。

> 对照：业务级项（验收标准可断言、数据约束精确、特殊字符行为、业务实体结构等）PRD 缺失时仍按 ❌ 处理、给修订建议、必要时列入待确认——这类不属于系统级能力豁免范围。

## 第二步：缺陷发现与修订建议

对自检未通过的项，逐一分析：
- 缺陷 ID（D-xx）
- 所在章节
- 问题描述
- 对用例生成/接口测试/脚本编写的影响
- 具体修订建议

断言覆盖中"需要产品补充=是"的检查点也作为缺陷输出，缺陷描述格式：「{元素名称} 的 {检查点} 未定义：{原因}」

**可测性分流（见 [assertion-coverage-checklist.md](assertion-coverage-checklist.md)「可测性三问」）**：每个必填检查点过"前置态可构造 / 断言可观测 / 清单有限集"三问；命中且**无法补全**的，作为一类缺陷输出、状态标 **🚫 不可测**，注明命中哪条 + 等待方（产品/研发——可能需开测试开关、给观测手段或有限清单）；**能补全**的就地改造成可观测/可构造断言（给构造途径/正向断言/逐项清单），不进缺陷。

## 第一步补充：多文档一致性核对（高价值缺陷来源）

当本期需求涉及**多份相关 PRD 文档**时（典型：`docs-bucket/<title>[<id>].md` 本期 PRD + `rag-bucket/【PRD】xxx.md` 拆分/兄弟 PRD + 被引用的关联 PRD），必须做交叉一致性核对——实践中**最有价值的缺陷往往是文档间冲突**，而非单文档内的缺失。

核对要点：
- **权限/可见性**：各文档对同一模块的角色可见性是否一致（例：A 文档说"教师可见"，B 文档说"本期隐藏不做" → 冲突）
- **数量/命名**：同一组功能/模块在不同文档里的数量与命名是否一致（例：A 文档列 7 个教师模块，B 文档列 6 个且命名不同）
- **交互行为**：同一交互在不同文档的描述是否冲突（例：A 文档"再次点击可收起" vs B 文档"展开后不可收起"）

发现冲突 → 作为**冲突类缺陷（D-xx）**输出，问题描述里**点名两份文档各自的表述**，等待方=产品。冲突类缺陷优先级通常高于单文档缺失。

> PRD 输入：`docs-bucket/<title>[<id>].md` 即本期 PRD（需求文档）；PRD 若拆成多份（如 `rag-bucket/【PRD】...`），把相关几份一并喂给分析器。**多份冲突时不预设哪份权威，记 D-xx 待产品裁定。**

## 第一步补充（二）：沿用/依赖锚点扫描 + 依赖边界反向核对（防漏读被沿用需求）

> 为什么单独一节：上面的「多文档一致性核对」是**冲突视角**（两份文档对同一件事说的是否打架）。但复用型需求（复用既有页面/逻辑）最常见的漏检不是"冲突"，而是**"我沿用了别的需求的某个能力，却没去读那个能力的边界，结果它的约束反过来卡住了我这份需求的前提假设"**。这类需求 PRD 里"沿用/复用/见 X/本期不改/已在 Y 交付"满屏都是，每一个都是一份**必读依赖**——但只有"依赖了它的能力"时才必须深读边界，"只沿用它的数据/长相"时不必。
>
> 真实踩坑（商品可售范围控制 7022520795）：PRD §6.7 明说"填写/编辑交互已在商品管理交付、本期不改"，分析时把商品管理只当"可见性口径核对"读了，没读它的**编辑时机/状态锁定**边界 → 漏掉了"商品销售中能否编辑可销售院校（决定'范围收窄'类用例前置能否构造）"这一环。PRD 没写编辑时机是**正常的（沿用既有、最小原则），不该让产品补**；该做的是 QA 去读被沿用的那份需求。

### 步骤 A：机械扫描沿用/依赖锚点（不可凭印象）

逐段扫 PRD 全文，命中以下任一信号即登记为一条"沿用/依赖锚点"，记录**锚点原文 + 章节位置 + 指向的文档/需求**：

```
沿用 | 复用 | 不改 | 本期不做 | 本期不改 | 保持现状 | 已交付 | 已在.*交付 |
见《…》 | 见 .*\.md | 关联知识库 | 依赖 需求\d+ | 与 .* 解耦 | 同 .* 一致 | 沿用现有
```

产出一张「被引用/被依赖文档清单」（锚点原文｜位置｜指向文档｜下一步动作）。清单为空（纯新功能、无沿用）→ 记一句"无沿用/依赖锚点"后跳过本节。

### 步骤 B：按风险分流（决定"要不要深读被沿用文档的边界"）

对每条锚点判"本需求沿用的是对方的什么"：

| 沿用的东西 | 处理 | 例 |
|---|---|---|
| **数据 / 展示规格 / 长相**（沿用它"长什么样、返回什么数据"）| **不深读**，只标"归属方 = 需求Z / 知识库Y，本需求不测（现状回归归其所属）"；若已误收成本需求 AC/BR → 剔除或标不测 | 「推荐区展示规则不变：竖图/窗口3个/最多10个」→ 归购买逻辑补充，本需求不测 |
| **能力 / 行为 / 状态 / 权限 / 前置态**（本需求的**前提或用例前置**依赖它"能不能做、什么状态下能做"）| **必须去读被引用文档的边界**，反问一句：**"它的边界/约束（状态锁定/编辑时机/前置条件/权限）会不会反过来卡住本需求的前提假设或用例前置？"** 命中 → 记 D-xx | 「编辑交互沿用商品管理」→ 必读商品管理的"销售中能否编辑"，因为它决定"范围收窄"类用例前置能否构造 |

> 判据一句话：**沿用"长什么样 / 什么数据" → 归对方、不深读；沿用"能不能做 / 什么状态能做" → 必读对方边界。**

### 步骤 C：命中后的缺陷定性（关键：多数不是"让产品补"）

依赖边界核对命中问题时，**先判该定义缺在谁那**：

- **对方文档（被沿用需求）已定义** → 直接把结论采纳进本需求的**前置条件链 / 用例前置**，不记缺陷（沿用既有、闭环）。
- **对方文档也没定义 / 需确认** → 记 D-xx，**等待方优先 = QA 自核（去读那份文档）或对方需求的产品**；**本需求 PRD 未写不算本需求 PRD 缺陷、不要求本需求产品补**（沿用既有逻辑，本 PRD 不重复定义是对的、符合最小原则）。
- 只有当"被沿用能力**在所有相关文档里都没定义**、且确需产品拍板"时，才升级为"产品补"——且指向**能力所属的那份需求**，不是本需求。

> 反模式（必避）：把"本需求 PRD 没写某沿用能力的边界"直接记成"本需求待产品补 PRD"。这是错的——沿用既有逻辑时本 PRD 留白是正确的，正解是 QA 去读被沿用的文档。
