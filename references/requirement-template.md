## 第 3 章：功能逻辑

每个功能（页面/流程）独立一节。功能划分优先按路由对应的页面，跨页面的流程单独成节。

### 3.N: [功能名称]

#### 3.N.1 功能目的

[一段话描述这个功能解决什么问题、在产品中的角色]

**提取方式**: 从页面组件的整体逻辑和用途推断。

#### 3.N.2 操作流程（多步骤/多分支场景）

当功能涉及多步骤操作或存在条件分支时，必须用流程图描述：

```
开始
  │
  ↓
用户点击"提交订单"
  │
  ↓
表单校验 ──校验失败──→ 显示错误提示，停留当前页
  │
  校验通过
  ↓
调用创建订单接口
  │
  ├── 成功 ──→ 跳转支付页
  │               │
  │               ├── 支付成功 ──→ 跳转订单详情（已支付状态）
  │               └── 支付失败 ──→ 显示支付失败提示，可重试
  │
  └── 失败 ──→ 显示错误提示，可重试提交
```

**提取方式**: 分析事件处理函数中的完整逻辑链，包括条件分支、API 调用、导航跳转、错误处理。

#### 3.N.3 状态机（多状态流转场景）

当功能涉及多个状态之间的流转时（如审批流、订单状态、工作流），必须用状态机描述：

```
┌─────────┐  提交审批  ┌─────────┐  审批通过  ┌─────────┐
│  草稿    │ ────────→ │ 审批中   │ ────────→ │ 已通过   │
│  draft   │           │ pending │           │ approved│
└─────────┘           └────┬────┘           └─────────┘
     ↑                      │ 审批驳回
     │                      ↓
     │                 ┌─────────┐
     └── 重新编辑 ←─── │ 已驳回   │
                       │ rejected│
                       └─────────┘
```

对每个状态记录：
| 状态 | UI 表现 | 可执行操作 | 转换条件 |
|------|---------|-----------|----------|
| 草稿 draft | 编辑表单可修改 | 编辑、删除、提交审批 | 点击提交→审批中 |
| 审批中 pending | 表单只读，显示审批进度 | 撤回 | 审批人通过→已通过；审批人驳回→已驳回 |
| 已驳回 rejected | 表单可修改，显示驳回原因 | 编辑、重新提交 | 点击重新提交→审批中 |
| 已通过 approved | 只读展示，显示通过时间 | 无 | 终态 |

**提取方式**: 从 `useReducer` 的 action types、`switch-case` 语句、状态变量组合中提取。

#### 3.N.4 交互规则

对每个可交互元素，描述完整的行为规则：

| 元素 | 交互方式 | 触发行为 | 前置条件 | 后续效果 |
|------|----------|----------|----------|----------|
| 提交按钮 | 点击 | 调用 API 提交表单 | 表单验证通过 | 成功→跳转列表页；失败→显示错误提示 |
| 搜索输入框 | 输入 | 实时过滤列表 | 无 | 输入为空时显示全部数据 |
| 删除按钮 | 点击 | 弹出确认对话框 | 用户有删除权限 | 确认后删除并刷新列表 |

**提取方式**: 分析所有事件处理函数（onClick, onChange, onSubmit 等）的完整逻辑。

#### 3.N.5 校验规则

| 字段/输入 | 规则 | 错误提示 | 校验时机 |
|-----------|------|----------|----------|
| 手机号 | 11位数字，1开头 | "请输入正确的手机号" | 失焦时 |
| 密码 | ≥8位，含大小写和数字 | "密码强度不足" | 提交时 |
| 邮箱 | 合法邮箱格式 | "请输入正确的邮箱" | 失焦时 |

**提取方式**: 从 zod/yup schema、自定义校验函数、`pattern` 属性中提取。

> 面向研发和测试，定义该功能"完成"的标准。

| 编号 | 验收条件 | 优先级 |
|------|----------|--------|
| AC-1 | [具体的、可验证的验收条件] | P0 |
| AC-2 | [具体的、可验证的验收条件] | P0 |
| AC-3 | [具体的、可验证的验收条件] | P1 |
| ... | ... | ... |

验收标准应覆盖：
- **正向路径**: 用户按正常流程操作能达到预期结果
- **逆向路径**: 异常输入/操作能得到合理反馈

- **状态约束**: 各状态下的操作权限正确

**提取方式**: 从功能的操作流程、交互规则、校验规则、极限场景中提炼可验证的条件。每个功能至少包含正向路径的验收条件。

## Requirement_log.md（同步生成）

> 每次同步 requirement.md 时，同步更新（追加）此文件。记录每次变更的详细信息，用于回溯和审计。

```markdown
# Requirement Change Log

| 序号 | 时间 | Git Commit | 更新模式 | 修改章节 | 修改内容 | requirement.md 版本 |
|------|------|------------|----------|----------|----------|---------------------|
| 1 | YYYY-MM-DD HH:mm | abc1234 (dirty) | full-rewrite | 全部 | 初始生成：从 demo 代码反向提取全部产品逻辑 | 1.0 |
| 2 | YYYY-MM-DD HH:mm | def5678 | incremental | 3.2 用户管理, 4.1 计算规则 | 新增用户删除确认弹窗；修正总价计算公式 | 1.1 |
```

### 字段说明

| 字段 | 说明 |
|------|------|
| 序号 | 自增编号 |
| 时间 | 同步操作的实际时间，精确到分钟 |
| Git Commit | 当前 HEAD 的短 commit hash。若有未提交的变更追加 ` (dirty)`；若无 git 仓库填 `N/A` |
| 更新模式 | full-rewrite / incremental / full-refresh |
| 修改章节 | 受影响的章节编号和名称，多个用逗号分隔 |
| 修改内容 | 简述具体改了什么，每个变更点用分号分隔 |
| requirement.md 版本 | 对应 @meta 中的 version |

### 写入规则
